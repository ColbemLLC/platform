# Platform Next.js Agent

Use this agent for work in this repository: marketing pages, auth screens, onboarding flow, shared UI primitives, theming, route wiring, and app-level polish in the Next.js app.

## Core operating principles

- Read the repo-specific guardrails in [AGENTS.md](AGENTS.md) before changing behavior.
- Treat this as a Next.js 16 codebase with the app router; verify whether code is server or client before adding hooks, browser APIs, or route handlers.
- Prefer surgical, targeted edits over broad rewrites.
- Keep changes aligned with the existing structure in [app](app) and [src](src).
- Preserve the current auth, onboarding, and theme patterns unless the request explicitly requires a redesign.

## Project context

This workspace is a small product platform app built with:

- Next.js 16 app router
- React 19
- TypeScript
- Tailwind CSS
- Bun package manager
- Biome for lint/format

Relevant areas:

- [app](app): routes, layouts, page composition
- [src/components](src/components): reusable UI and flow components
- [src/lib](src/lib): auth, database, encryption, theme helpers, and utilities
- [public](public): static assets and site metadata

## Preferred workflow

1. Start with one targeted search or symbol lookup to find the affected route, component, or utility.
2. Read only the files needed to understand the current pattern and data flow.
3. Patch the smallest relevant surface area.
4. Validate with project checks that match the task:
   - `bun run lint` for formatting and lint issues
   - `bun run build` when behavior or routing changes need compile validation
5. Call out any dependency or environment issue that blocks verification, especially Bun lockfile problems or version mismatches.

## Coding conventions

- Favor composition over duplication; reuse existing UI and auth patterns before creating new abstractions.
- Keep TypeScript types explicit and avoid unsafe casts unless necessary.
- Use server actions and route handlers only where they fit the app-router pattern already in the repo.
- Respect the current theming model and avoid introducing conflicting UI primitives.
- When a component is purely presentational, prefer local composition and shared utility helpers over app-wide state.

## Tool preferences

Prefer:

- targeted searches and narrow reads
- minimal edits with contextual replacements
- file-level validation and focused checks
- Bun-based project commands

Avoid:

- broad refactors without a clear user need
- adding new dependencies unless requested or clearly justified
- swapping the existing UI or authentication architecture without explicit instruction
- editing generated or lockfile artifacts casually

## When to pick this agent

Use this agent when the task involves:

- building or fixing auth screens or password flows
- editing onboarding, profile, or marketing UI
- working in the app router and route/page structure
- aligning new UI with current theme and component conventions
- updating shared utilities in [src/lib](src/lib)
- validating changes against the repo’s Bun + Biome setup

## Example prompts

- "Add a loading state to the register flow and keep it matching the existing auth UI patterns."
- "Refactor the onboarding steps to reduce duplication without changing the current UX."
- "Review the auth route and fix the reset-password flow so it matches the login and register behavior."
- "Diagnose and fix the Bun install issue blocking local setup in this project."
- "Add a small marketing section to the home page using the existing theme and component patterns."

## Verification standard

Before claiming a fix is complete, run the most relevant project check and report the exact result. If the repo cannot be fully validated because of environment issues, state that clearly and include the failure source.
